# MCP・エージェント設計（2026年3月版）

> Model Context Protocolの最新仕様とエージェント設計パターン

## 概要

Model Context Protocol（MCP）は、Anthropicが2024年11月にオープンソース公開したプロトコルで、LLMと外部ツール・データソースを標準的に接続するための仕様。2025年中にOpenAI・Google DeepMind・Microsoft・AWSなど主要プレイヤーが採用し、2025年12月にはLinux Foundation傘下のAgentic AI Foundation（AAIF）に寄贈された。2026年3月時点で事実上の業界標準となっている。

**エコシステム規模（2026年3月時点）:**
- 月間SDKダウンロード数: 9,700万以上
- アクティブサーバー数: 10,000以上
- MCPクライアント数: 300以上
- 対応ツール: ChatGPT、Claude、Cursor、Gemini、Microsoft Copilot、VS Codeなど主要AI全般

---

## 1. MCP最新仕様

MCPの仕様は段階的にリリースされている。主要バージョンは以下の通り:
- **2025-03-26**: Streamable HTTP Transport導入、SSE非推奨化
- **2025-06-18**: OAuth 2.1認証の大幅改定（リソースサーバー/認可サーバーの分離）
- **2025-11-25**: 非同期Tasks、URL Mode Elicitation、Extensions機構（最新安定版）

次期仕様は2026年6月頃を予定。

### Streamable HTTP Transport

**概要:** 従来のSSE（Server-Sent Events）トランスポートを非推奨とし、Streamable HTTPを標準トランスポートとして導入。

**変更点:**
- サーバーは単一のHTTPエンドポイント（例: `https://example.com/mcp`）を公開し、POSTとGETをサポート
- レスポンスにSSEを任意で使用可能（必須ではない）
- サーバーはセッションIDを `Mcp-Session-Id` ヘッダーで発行し、ステートフルなセッション管理が可能
- プロトコル自体はステートレスだが、アプリケーション層でステートフルなセッションをサポート

**使い方:**
- ローカル開発: stdio transport（従来通り）
- リモート/本番: Streamable HTTP transport
- stdioは引き続きサポートされるが、新規リモートサーバーはStreamable HTTPを採用すべき

```
クライアント → POST /mcp (JSON-RPC) → サーバー
クライアント ← HTTP Response or SSE Stream ← サーバー
```

### 非同期処理（Tasks）

**概要:** 2025-11-25で導入された実験的機能。任意のリクエストを「今呼び出し、後で取得」できるタスクとして実行可能にする。

**変更点:**
- 任意のMCPリクエストにタスクハンドルを付与可能
- タスクのステート: `working` → `input_required` → `completed` / `failed` / `cancelled`
- クライアントはポーリングで進捗確認・結果取得が可能
- サーバー定義の期間内で結果を保持

**使い方:**
- インデックス構築、レポート生成、大規模データ分析などの長時間処理に最適
- エージェントがタスクを起動し、並行して他の推論やユーザー対話を継続可能
- 医療データ分析やエンタープライズワークフローなど、数十万データポイントの処理に活用

### OAuth 2.1認証

**概要:** MCPサーバーへのセキュアなアクセス制御をOAuth 2.1ベースで標準化。

**変更点（2025-06-18〜2025-11-25）:**
- MCPサーバー = OAuth 2.1リソースサーバー（トークン検証を担当）
- 認可サーバーは外部（企業IdPなど）に分離
- PKCEが必須（クライアントシークレットなしの公開クライアント前提）
- RFC 9728（Protected Resource Metadata）でサーバーが認可サーバーの場所を公開
- RFC 8414（Authorization Server Metadata）で認可サーバーのメタデータを提供
- RFC 8707に基づくaudience検証が必須

**URL Mode Elicitation（2025-11-25）:**
- クライアント内でクレデンシャルを入力する代わりに、ブラウザでOAuth/支払いフローを完了
- APIキーやパスワードがMCPクライアントを経由しない
- PCI準拠の決済処理にも対応可能

**使い方:**
- 本番環境では必ずOAuth 2.1 + PKCEを実装
- 認可サーバーの分離により、既存のIdP（Auth0、Okta等）をそのまま利用可能
- 開発/ローカル環境ではトークン不要のstdioで十分

### その他の仕様変更（2025-11-25）

| 機能 | 概要 |
|------|------|
| **Extensions** | MCP仕様本体に含めずに機能を拡張する仕組み。サードパーティ拡張を標準的に定義可能 |
| **Elicitation強化** | デフォルト値サポート（string/number/enum）、複数選択enum、URL Mode Elicitation |
| **Server Instructions** | サーバーがクライアントに使い方のガイダンスを提供する仕組み（システムプロンプト的） |
| **Tool Annotations** | ツールのメタデータ（readOnly、destructive等）をアノテーションで宣言 |

## 2. MCPエコシステム

### 対応状況（主要ツール）

| カテゴリ | 対応ツール |
|----------|-----------|
| **AIアシスタント** | Claude Desktop、ChatGPT、Gemini |

| **フレームワーク** | LangChain、LlamaIndex、Vercel AI SDK、Spring AI |

### エコシステム規模

- **Agentic AI Foundation（AAIF）**: 2025年12月にLinux Foundation傘下で設立。MCP、Block社のgoose、OpenAIのAGENTS.mdが寄贈
- **AAIF参画企業**: Anthropic、OpenAI、Google DeepMind、Microsoft、AWS、Block、Meta、Intuit等
- **MCP Registry**: 2025年9月にプレビュー公開。サーバーの検索・発見を標準化
- **GitHub上のAI関連リポジトリ**: 110万以上（前年比+178%）
- **企業のエージェントAI導入**: 約65%がパイロットまたは本番稼働中（UiPath調査、2025年中期）

### セキュリティの現状

Astrix社の2025年調査によると:
- MCPサーバーの88%がクレデンシャルを要求
- 53%が長寿命の静的シークレットに依存（安全性に課題）
- OAuth採用率はわずか8.5%
- 本番運用では必ずOAuth 2.1への移行を推奨

## 3. 実用MCPサーバー厳選リスト

### Supabase MCP

**概要:** Supabaseプロジェクトの管理をAIツールから直接実行。データベース設計・クエリ・プロジェクト管理・ブランチ管理まで20以上のツールを提供。

**主要ツール:**
- プロジェクト作成・管理
- テーブル設計・スキーマ管理
- SQLクエリ実行・レポート生成
- Edge Functions管理
- Storage管理
- ログ取得・デバッグ

**導入方法:**
```json
{
  "mcpServers": {
    "supabase": {
      "command": "npx",
      "args": ["-y", "@supabase/mcp-server"]
    }
  }
}
```
- 2025年10月にリモート（クラウドホスト型）MCP サーバーをリリース
- OAuth認証によるブラウザログインに対応（PAT不要）
- `read_only` パラメータで読み取り専用モードも利用可能
- `features` パラメータでツールグループの有効/無効を制御可能

### GitHub MCP

**概要:** GitHub公式のMCPサーバー。リポジトリ操作、Issue/PR管理、Actions監視、コード分析をAIから直接実行。

**主要ツール:**
- リポジトリのブラウズ・コード検索・コミット分析
- Issue/PRの作成・更新・管理
- GitHub Actionsの監視・ビルド失敗分析
- セキュリティスキャン結果・Dependabotアラートの確認
- GitHub Projects管理

**導入方法:**
```json
{
  "mcpServers": {
    "github": {
      "command": "docker",
      "args": ["run", "-i", "--rm",
        "-e", "GITHUB_PERSONAL_ACCESS_TOKEN",
        "ghcr.io/github/github-mcp-server"]
    }
  }
}
```
- **Lockdownモード**: プロンプトインジェクション対策のコンテンツフィルタリング
- **Server Instructions**: ツール間の依存関係やワークフローをガイド
- **ツール統合**: 複数操作を単一ツールに統合し、コンテキストウィンドウ使用量を削減

## 4. エージェント設計パターン

### いつMCPを使うべきか

- **外部サービスとの統合が必要な場合**: データベース、API、SaaS等への標準的なアクセスレイヤーが必要な時
- **複数のAIクライアントから同じツールを使う場合**: 一度サーバーを作れば、Claude/ChatGPT/Cursor等すべてから利用可能
- **認証・認可が必要な場合**: OAuth 2.1ベースのセキュアなアクセス制御が標準で利用可能
- **長時間処理が必要な場合**: Tasksによる非同期処理でバックグラウンド実行が可能
- **段階的な導入**: まず読み取り専用サーバー（ドキュメント検索、監視）から始め、書き込み系を後で追加

### いつMCPを使うべきでないか

- **単純なAPI呼び出し1回で済む場合**: 直接HTTPリクエストの方がオーバーヘッドが少ない
- **リアルタイム双方向ストリーミングが必要な場合**: MCPはリクエスト-レスポンスモデル。WebSocketの方が適切
- **LLMを介さない自動化**: MCPはLLMがツールを呼ぶためのプロトコル。従来のRPCやAPIゲートウェイで十分な場合は不要
- **機密性の極めて高いオペレーション**: エージェントに直接的な制御を委ねるべきでない操作（本番DBの直接変更など）

### マルチエージェント設計のベストプラクティス

**主要プロトコルの使い分け:**

| プロトコル | 用途 | 提供元 |
|-----------|------|--------|
| **MCP** | エージェント ↔ ツール/データの接続 | Anthropic → AAIF |
| **A2A** | エージェント間のピアツーピア協調 | Google |
| **ACP** | エンタープライズガバナンス・コンプライアンス | IBM |

**Googleの8つのマルチエージェント設計パターン:**
1. **Sequential Pipeline**: タスクを順番に処理
2. **Parallel Fan-out**: 独立したタスクを並行実行
3. **Routing**: タスクの種類に応じて適切なエージェントに振り分け
4. **Orchestrator-Worker**: 中央オーケストレーターがワーカーに指示
5. **Evaluator-Optimizer**: 結果を評価し改善ループを回す
6. **Human-in-the-Loop**: 重要な判断にヒューマンレビューを組み込む
7. **Multi-Agent Debate**: 複数エージェントの議論で精度向上
8. **Hierarchical**: 階層的な指揮系統

**コンテキスト管理パターン:**
- **Progressive Disclosure**: ツールの短い説明だけを先に渡し、必要時のみ詳細を読み込む（Cursorが採用）
- **File-based Offloading**: 古いツール結果をファイルに書き出し、コンテキストウィンドウを節約（Manusが採用）
- **Skills as Folders**: スキルをフォルダ+YAMLフロントマターで管理し、必要時のみ全文読み込み（Anthropicが採用）

### ツール設計のベストプラクティス

**命名と説明:**
- ツール名は一意で説明的に（略語を避ける）
- 説明は1〜2文で「動詞 + リソース」構造にする
- 認証やページネーションの詳細はスキーマ側に記載

**スコープ設計:**
- 1ツール = 1つの明確なタスク。無関係な操作を1ツールに詰め込まない
- JSON Schemaで全入力パラメータを検証（型情報、必須フィールド、説明を含む）
- 構造化されたJSON出力 + テキストブロックの両方を返す（後方互換性）

**セキュリティ:**
- 読み取り専用サーバーから始める（ドキュメント検索、監視、可観測性）
- サーバーごとにブラストラディウスを限定（プロジェクト単位のキー、制限されたディレクトリ、dev/testデータ）
- 誰が何を呼んだかをログに記録
- stdioでの標準出力は行わない（MCPクライアントの動作を阻害する。ファイルベースのロギングを使用）

**本番運用チェックリスト:**
- [ ] OAuth 2.1 + PKCEを実装
- [ ] ツールにannotation（readOnly/destructive等）を付与
- [ ] 読み取り専用モードをデフォルトに
- [ ] アクセス範囲を最小限に制限
- [ ] 監査ログを有効化
- [ ] エラーハンドリングで機密情報を露出しない
